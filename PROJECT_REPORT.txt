2. HOW TO RUN / WORK WITH THE PROJECT
--------------------------------------------------------------------------------

  1) Install:        composer install && npm install
  2) Env:            copy .env.example -> .env, set DB + mail, then:
                     php artisan key:generate
  3) Database:       php artisan migrate --force && php artisan db:seed
                     (migrations + seeders live inside each module)
  4) Assets:         npm run build          (Tailwind v4 + Vite; rebuild after
                                             ANY resources/css or module css change)
  5) Serve:          php artisan serve --port=8001
  6) Tests:          php artisan test              (full suite)
                     php artisan test --filter=<Name>   (single suite/test)
                     NOTE: tests use RefreshDatabase — the local dev DB is
                     NOT touched by tests.

  Known dev quirks:
   - `npm run build` prints a pre-existing `@source` warning — ignore it.
   - After editing blade views while `php artisan serve` runs, run
     `php artisan view:clear` defensively (Blade usually recompiles itself).
   - When verifying pages with curl, login requires a CSRF token (see §11).
   - Auth requests are rate limited: auth = 5/min per IP, checkout = 3/min.

5b. 2FA + GOOGLE SIGN-IN (2026-08-19)
--------------------------------------------------------------------------------
 Two-factor authentication (user's choice of TOTP authenticator app or email
 code) and Google OAuth sign-up/login, built on the custom auth stack:

   - Password login /accessaccount: validates credentials WITHOUT logging in,
     then defers to /2fa/challenge when 2FA is enabled (session key 2fa.pending).
   - Challenge: TOTP via pragmarx/google2fa (30s window, 1-step tolerance,
     replay protection via 2fa:totp-ts cache) or 6-digit email OTP (hashed in
     cache, 10-min TTL, 60s resend cooldown). 5 wrong codes invalidates the
     session (throttle:2fa 5/min/IP + per-session cap).
   - Enrollment on /profile/settings: TOTP QR (SVG, offline), email codes,
     disable requires current password. 5 failed confirmations reset pending.
   - Admin enforcement: login sets session flag 2fa.required for admins
     without 2FA; 2fa.enrolled middleware gates the admin route group to
     /profile/settings until confirmed (flag-based -> actingAs tests unaffected).
   - Google OAuth (laravel/socialite): /auth/google/redirect + /callback.
     Auto-links existing email, auto-creates a 'user' account when the email is
     new (password null), rejects a Google id already linked to a different
     email. Google logins with 2FA fall through the same challenge flow.
   - Google-only accounts cannot password-login ("This account uses Google
     sign-in."). Audit events via Log::info (auth.2fa_* / auth.google_*).
   - Dependencies: laravel/socialite 5.30, pragmarx/google2fa-laravel 3.0.1,
     simplesoftwareio/simple-qrcode 4.2. Server needs php8.3-gd (installed).
- Config: GOOGLE_CLIENT_ID / GOOGLE_CLIENT_SECRET set on the server .env;
      authorized redirect URI https://smartshop-luwi.tech/auth/google/callback
      (only required field; JS origins optional for the server-side flow).
      The button is now fully functional on production.

6. DESIGN SYSTEM & CODE CONVENTIONS
--------------------------------------------------------------------------------

 Global CSS lives in resources/css/app.css (shared tokens + all component
 classes). Console-specific classes (partner dashboard) live in
 Modules/PartnerHub/resources/css/partner.css; admin dashboard uses
 dashboard.css. Both are loaded via @section('styles')/@vite on console pages.

 7.4 Shell + tabs architecture (IMPORTANT — learn this)
   <x-profile-layout :user :stats :active :identity> renders: identity header
   (avatar+upload, name, role badge, verified badge, tier badge, member since),
   stats tiles, then INCLUDES partials/profile-tabs (passing user + active), then
   the identity details card when :identity=true, then the page slot.
   partials/profile-tabs.blade.php ECHOES the <nav class="profile-subnav"> and
   computes per-role tab arrays (href/label/active) via match(user->role):
     buyer  : Overview(/profile) Orders(/orders) Address&Security Settings
     admin  : Overview(/admin/profile) Command Center(/admin/dashboard)
              Address&Security Settings
     partner: Overview(/partner/profile) My Orders(/partner/orders)
              Address&Security Public Profile(/partner/profile/edit)
   The shell component itself does NOT define the tabs — the partial owns them.

   BLAZE SCOPE GOTCHA: Blade @include renders in a child scope — variables
   assigned inside an included partial DO NOT leak into the parent template.
   That is why the partial must echo markup instead of setting $profileTabs.

11. ENGINEER HANDOFF NOTES (gotchas & procedures)
--------------------------------------------------------------------------------

   - Blade include scoping: variables set in an @include do NOT propagate to the
     parent (see §7.4). To share per-role data, echo markup from the partial or
     compute in the component/controller.
   - Route naming constraints: existing names are frozen; add-only policy.
   - Rate limits: auth 5/min/IP, checkout 3/min/IP (TelemetryPipeline
     RateLimiter::for). Excess login attempts -> silent 302 back to /login
     (the login view renders no error banner — don't chase "no error shown").

13. RESPONSIVE DESIGN ASSESSMENT (2026-08-18 — audit) AND RESOLUTION (0cec31e)
--------------------------------------------------------------------------------
 RESOLVED 2026-08-18 in 0cec31e. Both issues fixed and re-verified with the
 same CDP audit script at 1280/768/390: /shop, /product/73, /admin/products
 all scrollWidth <= clientWidth. Root cause of the product page turned out
 to be a cross-module class collision: MarketplacePipeline's scss still
 shipped a DEAD .product-info{display:flex} rule (no view uses it) that
 leaked onto the CatalogDelivery product page info column and re-arranged
 it as a non-wrapping flex row once min-width:0 collapsed the grid track.
 Removal of the dead rule + min-width:0 on .product-details children fixed
 the page at every width. Pagination styles moved from the blade <style>
 into app.css (PAGINATION block) with a <=768px flex-wrap rule. 48 tests /
 182 assertions green; zero inline styles; only <style> left is the email.
 LESSON: module asset bundles load globally via @vite (app-layout) — class
 names must be module-prefixed or verified dead-code-free across modules;
 add a cross-module class-collision grep to future verification passes.

 Method: agent-browser (CDP) against :8001; 67 page/viewport checks across
 29 distinct pages at 1280 / 768 / 390 widths; measured page-level horizontal
 overflow (documentElement.scrollWidth > clientWidth) plus offending element
 geometry. Auth sessions: user2@test.com (buyer), artisan@test.com (partner),
 admin@test.com (admin); guest pages tested logged out.

 VERDICT: GOOD. The responsive work done pre-migration (8b33db9/8f32d99 era)
 survived the modular monolith move; the only breakage is two small, easily
 fixable items. Profile pages built in the separation phase are clean at all
 widths (subnav + identity rows + form pairs collapse correctly; pc-nav and
 profile-subnav tabs scroll horizontally by design on small screens).

 ISSUES FOUND (2 root causes, affecting 3 page types):

 1) PRODUCT PAGE — horizontal overflow below ~790px (found at 768 AND 390).
    Symptom: .gallery / .main-image-container / .product-info stay ~758px wide
    on a 375-768px viewport; page scrolls sideways.
    Root cause: .product-details is `display:grid; 1fr 1fr` collapsing to 1fr
    under 768px, but the grid CHILDREN have no `min-width: 0`, so the single
    track takes the .gallery's min-content width = the main image's intrinsic
    width (~756px). The img has `max-width:100%` but that does not reduce
    min-content contribution in grid.
    Files: Modules/CatalogDelivery/resources/assets/scss/app.scss
           (.product-details ~line 309, .gallery ~line 317,
            .main-image-container ~line 322, 768px block ~line 411).
    Fix (later): min-width:0 on .gallery/.product-info and/or
    .main-image-container img { width:100%; height:100%; object-fit:cover }.

 2) PAGINATION COMPONENT — horizontal overflow at 390 (34px) on any page with
    more than one page of records: /shop and /admin/products confirmed (also
    affects /admin/users, /admin/orders, /admin/partners, /admin/reviews,
    partner inventory/orders once they exceed one page).
    Symptom: .pagination-inner is 442px wide, centered (l:-33), never wraps.
    Root cause: shared partial resources/views/partials/pagination.blade.php
    embeds its CSS in a <style> block inside the blade; .pagination-inner uses
    flex + gap:1.5rem with no wrap and no overflow handling.
    Secondary issue: CSS embedded in the blade violates the project convention
    (styles belong in resources/css/app.css) — the earlier zero-inline sweep
    only checks style="" attributes, so this passed unnoticed.
    Fix (later): move pagination styles to app.css and add a mobile rule
    (e.g. overflow-x:auto on .luxury-pagination or allow wrap/smaller gaps).

 VERIFIED NON-ISSUES:
   - filter-drawer on /shop: off-canvas via translateX(100%), does NOT extend
     scrollWidth at rest (Chrome excludes fixed-position overflow); the 390px
     /shop overflow is fully explained by the pagination component.
   - pc-nav tabs + profile-subnav tabs: overflow-x:auto + nowrap = intended
     horizontal-scroll pattern on mobile; not page overflow.
   - inventory/orders/payouts tables: wrapped in .pc-table-wrap /
     .inventory-table-wrap (overflow-x:auto) — correct pattern.
   - All legal pages, auth pages, buyer pages, partner console, admin
     dashboard/users/orders/payouts/reviews/partners/profile: no overflow at
     any tested width.
