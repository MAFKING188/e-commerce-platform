\section{Phase 0: Readiness \& Prerequisites}
Before initiating the server-side deployment, I ensured that all foundational assets were in place. This phase was critical for a seamless "Git-to-Server" transition.

\begin{itemize}
    \item \textbf{GitHub Repository:} The SmartShop codebase was finalized and pushed to a private repository.
    \item \textbf{Domain Name:} I registered \texttt{smartshop-luwi.tech} via the GitHub Student Pack.
    \item \textbf{SSH Credentials:} I generated a local SSH key pair and added the public key to my DigitalOcean account to ensure secure, passwordless access to the Droplet.
    \item \textbf{Database Dump:} A local export of the development database (\texttt{database\_dump.sql}) was prepared for the hybrid import strategy.
\end{itemize}

\section{Phase 1: Infrastructure \& Resource Management}
I provisioned a DigitalOcean Droplet with \textbf{Ubuntu 24.04 LTS} on the \$6/month plan. To ensure future-proofing and stability, I implemented VPC networking and Swap memory.

\subsection{VPC Networking}
I created a private network (\texttt{smartshop-vpc}) in the same region as my Droplet to isolate internal traffic and allow for secure communication with future services.

\subsection{Resource Management: Swap Memory Implementation}
During the early stages of service installation, I encountered "Out of Memory" (OOM) errors. To stabilize the 1GB RAM environment for MySQL, I implemented a 2GB Swap file:
\begin{lstlisting}[language=bash]
sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
\end{lstlisting}

\subsection{Initial Server Hardening}
\begin{lstlisting}[language=bash]
sudo apt update && sudo apt upgrade -y
sudo apt install -y git curl unzip zip nginx supervisor
\end{lstlisting}

\section{Phase 2: The Production LEMP Stack}
The application requires a specific version of PHP and a secured MySQL instance.

\subsection{PHP 8.3 Installation}
I used the Ondrej PPA to source the required PHP 8.3 modules:
\begin{lstlisting}[language=bash]
sudo add-apt-repository ppa:ondrej/php -y
sudo apt update
sudo apt install -y php8.3-fpm php8.3-mysql php8.3-mbstring php8.3-xml php8.3-bcmath php8.3-curl php8.3-zip php8.3-intl
\end{lstlisting}

\subsection{MySQL: Installation, Recovery \& Security}
Due to an OOM crash during the first attempt, I had to ensure the service was correctly enabled and started after implementing Swap.
\begin{lstlisting}[language=bash]
sudo apt install -y mysql-server
sudo systemctl enable mysql
sudo systemctl start mysql
\end{lstlisting}

I then executed the \texttt{mysql\_secure\_installation} script with the following parameters:
\begin{itemize}
    \item Validate Password Plugin: \textbf{No} (to maintain flexibility during setup).
    \item Remove Anonymous Users: \textbf{Yes}.
    \item Disallow Remote Root Login: \textbf{Yes}.
    \item Remove Test Database: \textbf{Yes}.
\end{itemize}

\subsection{Production Database Initialization}
\begin{lstlisting}[language=bash]
sudo mysql -u root

CREATE USER 'luwi'@'localhost' IDENTIFIED BY 'StrongPasswordHere';

\section{Phase 3: Git Integration \& Server-Side Repository Setup}
With the server environment stabilized, the next critical step was the secure integration of the SmartShop codebase from GitHub.

\subsection{SSH Key Configuration (Server to GitHub)}
To allow the Droplet to pull code securely without repeated password prompts, I configured a deployment key:
\begin{lstlisting}[language=bash]
# Generating the key on the Droplet
ssh-keygen -t ed25519 -C "deployment@smartshop-luwi.tech"
# Displaying the key to be added to GitHub Repository Secrets/Deploy Keys
cat ~/.ssh/id_ed25519.pub
\end{lstlisting}

\subsection{The Repository Clone \& "Safe Directory" Resolution}
I cloned the repository into the standard web root. A specific security hurdle encountered was Git's \texttt{safe.directory} requirement when operating in a directory owned by another user (or root):
\begin{lstlisting}[language=bash]
cd /var/www
# Cloning using SSH for security
git clone git@github.com:yourusername/e-commerce-platform.git smartshop
# Resolving the ownership conflict to allow Git operations
git config --global --add safe.directory /var/www/smartshop
\end{lstlisting}

\subsection{Filesystem Permissions for Git \& Laravel}
I ensured that the repository files were owned by the Nginx user while maintaining Git's ability to track changes:
\begin{lstlisting}[language=bash]
sudo chown -R www-data:www-data /var/www/smartshop
sudo chmod -R 775 /var/www/smartshop/storage
sudo chmod -R 775 /var/www/smartshop/bootstrap/cache
\end{lstlisting}

\section{Phase 4: Environment Configuration \& Data Recovery}
This phase involved the transition from development settings to production-specific values.

\subsection{The Terminal Configuration Fix}
When attempting to use \texttt{nano} to edit the environment variables, I encountered the error \texttt{Error opening terminal: xterm-kitty}. I resolved this by resetting the terminal type for the session:
\begin{lstlisting}[language=bash]
export TERM=xterm
nano .env
\end{lstlisting}

\subsection{The Hybrid Data Strategy}
Instead of relying solely on migrations, which might lack development-time data, I imported my local dump after verifying the current database state:
\begin{lstlisting}[language=bash]
# Verify the target database is ready
sudo mysql -e "USE smartshop; SHOW TABLES;"
# Perform the import
mysql -u luwi -p smartshop < database_dump.sql
# Synchronize Laravel migration status
php artisan migrate:status
\end{lstlisting}

\subsection{Application Key Generation}

\section{Phase 5: Nginx Configuration \& SSL Security}
With the application configured, I set up the web server to route traffic and secured it with encryption.

\subsection{Nginx Site Setup}
I created a dedicated configuration for SmartShop and disabled the default Nginx welcome page:
\begin{lstlisting}[language=bash]
sudo nano /etc/nginx/sites-available/smartshop
sudo ln -s /etc/nginx/sites-available/smartshop /etc/nginx/sites-enabled/
sudo rm /etc/nginx/sites-enabled/default
\end{lstlisting}

The configuration explicitly points to the \texttt{/public} directory and handles PHP processing via the 8.3 FPM socket:
\begin{lstlisting}[language=bash]
server {
    listen 80;
    server_name smartshop-luwi.tech www.smartshop-luwi.tech;
    root /var/www/smartshop/public;
    index index.php index.html;
    location / {
        try_files $uri $uri/ /index.php?$query_string;
    }
    location ~ \.php$ {
        include snippets/fastcgi-php.conf;
        fastcgi_pass unix:/run/php/php8.3-fpm.sock;
    }
}
\end{lstlisting}

\subsection{DNS Propagation \& SSL (Certbot)}
After verifying that the DNS A records for \texttt{smartshop-luwi.tech} had propagated, I issued a Let's Encrypt certificate:
\begin{lstlisting}[language=bash]
sudo apt install -y certbot python3-certbot-nginx
sudo certbot --nginx -d smartshop-luwi.tech -d www.smartshop-luwi.tech
\end{lstlisting}

\section{Phase 6: Supervisor \& Queue Management}
Production systems require background workers to handle emails and complex logic without slowing down the user experience.

\subsection{Environment Setup for Emails}
I configured the application to use the \texttt{database} queue driver and established a secure SMTP connection via Gmail.
\begin{lstlisting}[language=bash]
# Inside .env
QUEUE_CONNECTION=database
MAIL_MAILER=smtp
MAIL_HOST=smtp.gmail.com
MAIL_PORT=587
MAIL_USERNAME=your-email@gmail.com
MAIL_PASSWORD=your-16-digit-app-password
MAIL_ENCRYPTION=tls
\end{lstlisting}

\subsection{Supervisor Configuration}
I installed Supervisor to manage the Laravel queue worker, ensuring it restarts automatically if it crashes or the server reboots:
\begin{lstlisting}[language=bash]
sudo apt install -y supervisor
sudo nano /etc/supervisor/conf.d/smartshop-worker.conf
\end{lstlisting}

The configuration targets the \texttt{database} queue and runs as the \texttt{www-data} user:
\begin{lstlisting}[language=ini]
[program:smartshop-worker]
process_name=%(program_name)s_%(process_num)02d
command=php /var/www/smartshop/artisan queue:work --sleep=3 --tries=3 --timeout=90
autostart=true
autorestart=true
user=www-data
numprocs=1
redirect_stderr=true
stdout_logfile=/var/www/smartshop/storage/logs/worker.log
stopwaitsecs=3600
\end{lstlisting}

\subsection{Worker Activation \& Maintenance}
\begin{lstlisting}[language=bash]
sudo supervisorctl reread
sudo supervisorctl update
sudo supervisorctl restart smartshop-worker:*
# Clear any stuck failed jobs
php artisan queue:flush
\end{lstlisting}

\end{lstlisting}

\subsection{Production Email Troubleshooting}
During deployment, I identified that the worker could log "DONE" even if the external SMTP provider (e.g., Gmail) blocks the message for security reasons. The following diagnostic protocol was established:
\begin{itemize}
    \item \textbf{Worker Logs:} Monitor \texttt{tail -f storage/logs/worker.log} to confirm the job is processed.
    \item \textbf{Failed Jobs:} If the worker shows "Failed," use \texttt{php artisan queue:failed} to see why.
    \item \textbf{SMTP Relay:} For Gmail, an "App Password" must be used instead of the standard account password.
    \item \textbf{SPF/DKIM:} To ensure high deliverability, DNS TXT records for SPF and DKIM should be added to the domain settings.
\end{itemize}
